# Events, payments, and admin production plan

Reviewed: 2026-11-05. Scope: static review of the Go API, Next.js registration/payment/admin flows, models, migrations, jobs, and provider documentation. No application tests or live payments were run. Findings below describe code paths, not verified production incidents.

## Assessment

The project has useful foundations: server-calculated category prices, payment records and event history, receipt jobs, versioned waivers, route-level permissions, audit logging, and unique constraints for bibs, receipts, and check-in records. It is not ready to collect event payments through PesaPal: current provider implementations are Stripe and direct M-Pesa, and several shared registration/payment/race-day invariants need repair first.

## Delivery sequence

### 1. Close data exposure and define the contract

First close the existing-registration disclosure. Return minimal creation DTOs and use verified email links or short-lived scoped access tokens for recovery, payment initiation, confirmation downloads, and participant edits. UUIDs currently act as bearer capabilities; define their scope, expiry, and revocation rather than treating them as customer authentication. Keep medical data and receipts private, including generated files currently stored under the media path.

Require explicit waiver acceptance and submitted waiver version; reject stale versions with a clear reread prompt. Normalize emails and phone numbers, validate field types/options/lengths, and define required race information by event/category. Decide whether the payer can register multiple athletes or minors: event/email uniqueness currently prevents shared-email family entries. Separate payer identity from participant identity if that is supported. Define a guardian flow where needed.

Update `backend/openapi/openapi.yaml` before implementation. Record allowed state transitions, error codes, idempotency behavior, request examples, and minimal public/admin DTOs. Add versioned database migrations with a duplicate-data cleanup plan before changing constraints.

### 2. Repair payment and registration invariants

Use an immutable registration quote containing amount, currency, event/category, price version, and expiry. Enforce capacity using transactional reservations with expiry; define what happens when money arrives after a reservation expires or an event is cancelled. Require a category for categorized events. Validate dates, nonnegative prices, capacity, bib ranges and overlap before publishing. Prevent deletion of categories/events referenced by registrations; archive them and preserve historical snapshots.

Keep registration eligibility separate from payment-attempt status. Define pending, submitting/unknown, successful, failed, cancelled, and refund states explicitly. A timeout during provider submission must remain recoverable: it does not prove that no provider order exists. Confirm exactly once after verified payment, reject new checkout for a settled entry, and flag a second successful charge for finance recovery. Late failures must not downgrade success. Late success after cancellation must follow an explicit review/refund policy.

Idempotency requirements:

- Bind every key to the operation, target, provider, caller capability and normalized request fingerprint. Same key and same request returns the saved result; same key and different request returns conflict.
- Claim keys atomically with a unique constraint; persist in-progress/result/error states. Concurrent callers receive the same attempt or an explicit retry response.
- Allow one active checkout attempt per registration quote, even when callers generate different keys. Define retry/expiry rules and keep every attempt for audit.
- Use a stable merchant reference for an uncertain provider submission. Query/reconcile before resubmission; do not assume PesaPal supports a generic idempotency header.
- Treat notification delivery separately from processing. Persist an inbox item, verify provider status, then lock and update payment/registration plus an outbox in one transaction. Duplicate delivery must resume incomplete work. Do not deduplicate all future status changes solely by order tracking ID.
- Give refunds their own operation IDs, amount ledger, concurrency guards and provider evidence. Track partial totals and prevent cumulative over-refunds.

### 3. Implement PesaPal API 3.0

Add a provider adapter for authentication/token refresh, order submission, transaction-status retrieval and supported refund/cancellation operations. Configure sandbox/live base URLs, credentials, IPN registration ID and server-controlled callback URLs independently. Fail startup on missing production secrets/configuration. Confirm merchant activation, payment methods and currencies with the merchant account before advertising them.

Register an IPN endpoint once per environment and store its notification ID. Submit the saved quote and validated payer billing/contact details; persist local merchant reference, PesaPal tracking ID, redirect URL and submission outcome. Send the browser to hosted checkout.

Both browser return and IPN must request authoritative transaction status from PesaPal. Match the merchant reference, tracking ID, amount and currency to the stored attempt before granting entry. Treat inbound notifications as prompts to verify, never proof of payment. Validate their shape, bound their size/rate, acknowledge according to the provider contract, and process recoverably.

Add scheduled recovery for stale pending/unknown attempts and failed verification, with backoff, provider rate limits, retry budgets and finance alerts. Customer pages must show pending, paid, failed, cancelled and verification delayed accurately, and support recovery after closing the browser or switching devices.

PesaPal references: [SubmitOrderRequest](https://developer.pesapal.com/how-to-integrate/e-commerce/api-30-json/submitorderrequest), [RegisterIPNURL](https://developer.pesapal.com/how-to-integrate/e-commerce/api-30-json/registeripnurl), [GetTransactionStatus](https://developer.pesapal.com/how-to-integrate/e-commerce/api-30-json/gettransactionstatus). These specify IPN registration and server-side status lookup; account-specific refund/payment-method capabilities remain to be established.

### 4. Make the admin console an operations tool

Build an event workspace connecting setup readiness, entries, payments, bibs, collection, check-in and results. Add server pagination/search/filtering, per-action permission controls, safe loading/error states, and clear explanations for blocked actions.

Give each participant a detail view with quote, contact/race fields, consent version, eligibility, all payment attempts, refunds, bib and collection history. Give finance a payment timeline with merchant/tracking references, verified status, last check, retry history, receipt delivery and reconciliation exceptions. Provide audited status refresh, retry delivery, and recovery actions with reasons and appropriate permissions.

Remove arbitrary status editing. Model complimentary entries, cancellation, refunds, bib replacement and check-in correction as separate authorized operations. Confirm high-impact actions with the participant/event/amount shown; prevent duplicate submissions in the UI and API. Show manual refund recording distinctly from provider-confirmed money movement.

Create minimal event-scoped race-day lookup endpoints so staff can work without full registration or finance access. Define roles for event manager, finance, race-day staff, support and administrator; check permissions on the server and on every visible action. Add immediate disable/session revocation, safe refresh rotation, and MFA for privileged accounts. Move session credentials to secure HttpOnly cookies or a server session layer, with CSRF controls appropriate to that design. Redact medical/contact values in audit snapshots and restrict their access separately.

### 5. Repair bibs and race day

Allocate bibs transactionally with category/event locking, deterministic ordering and an advanced in-memory counter. Account for manually occupied numbers and overlapping ranges. Preserve existing assignments on rerun. Return actionable conflict/range-exhaustion results. Keep database uniqueness as the last safeguard.

Enforce eligibility, category range, event scope and lock rules for every assignment/replacement. Separate bib/pack collection from race check-in, preserve original timestamps on duplicate requests, and audit corrections with actor and reason. Require a real assignment before marking a bib collected. Add participant lookup by name/reference/bib, and consider QR lookup once its access scope is defined. Expose the assigned bib and event-local date/location/collection instructions in customer confirmation. Calculate age on race date and export actual team data.

### 6. Production acceptance and release

Use a transactional outbox for receipts/confirmation jobs, idempotent consumers, worker leases with crash recovery, explicit resend operations and failed-job recovery. Keep registration-received and payment-confirmed messages distinct. Reconcile successful payments against entries and settlement records; show gross, fees, refunds and net separately per currency.

Before launch, prove concurrent checkout/key conflicts, duplicate/delayed/out-of-order IPNs, missing browser returns, provider timeouts, crash between verification and commit, duplicate success charges, stale reservations, partial/refund retries, and email failures. Prove capacity and bib allocation under concurrency, unpaid/cancelled check-in rejection, locked bib behavior, role boundaries and disabled-session revocation. Include frontend flows with real API integration, then PesaPal sandbox acceptance and an authorized controlled live payment/refund.

Release only with observable payment failures/pending age, reconciliation exceptions, queue failures and audit coverage; tested backup/restore and migration rollback procedures; production email delivery; and a support runbook for paid-but-unconfirmed, duplicate payment, late payment, refund and race-day connectivity incidents.

## Decisions to settle during implementation

Payer versus athlete/group registrations; required participant/medical/guardian fields; reservation duration and late-payment policy; complimentary entries; refund/transfer rules; bib timing and ranges; race-day connectivity requirements; merchant methods/currencies and settlement format. These choices affect implementation but do not block fixing the confirmed defects above.

## Review limits and tooling

This is a static code review and prioritized implementation plan, not a production certification. Existing tests were located but not run. Production infrastructure, live database contents, merchant credentials/settings and live provider behavior were not inspected. Orbit discovery returned an unrelated NovaBilling wrapper rather than PesaPal's merchant API; it was not reused. Official PesaPal documentation supplied the provider contract references. The installed Postman CLI rejects `postman status` as an unknown command; no Postman workspace was created or modified.
